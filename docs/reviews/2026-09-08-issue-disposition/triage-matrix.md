## Notes

- **How this was read.** Tree at `29cfaf0`, verified before and after (the worktree
  `quietinbox-wt-28` and `main` are both at that commit and clean). Every row was checked against
  the code and the tests, not against the CHANGELOG. The commit carrying nine of the ten items is
  `389d7ce` ("Onboarding could report a capture test it had not run, and the health page hid its own
  uncertainty"); D4 is `a258662` / `022b99a` / `4797b13`.
- **Why so many DONE_UNTESTED.** `feature/health` has no test source set at all (`src/main` is its
  only directory) and nothing anywhere references `HealthScreen`, `lastCommittedAtEpochMs` or
  `lastEventAtEpochMs`. Every health-page item is therefore untested by construction, whatever its
  backend half looks like.
- **H4 is a deliberate refusal of the literal request, not an oversight.** The issue asked for "last
  system callback"; `lastEventAtEpochMs` is stamped inside `enqueue`
  (`CaptureCoordinator.kt:915`), which runs *after* the source filter (`:888-899`) and only when the
  bounded queue accepted the item — a callback for a disabled source, or one that overflowed, never
  reaches it. Labelling it "last system callback" would have manufactured a dishonest label, so it
  is called "last accepted event" (`strings.xml:239`) and the kdoc at `CaptureCoordinator.kt:60-65`
  records the argument. The item's own 缺什麼 (rendered in one hero arm only, absent from the
  diagnostics summary) is fully closed. A true last-callback stamp would be a separate field written
  before any filtering; the obstacle is the honesty argument, not the cost — `enqueue` already does
  a `_status.update` on that path.
- **A stale timeout job can report a premature failure on a retry (O8 residue, not covered by any
  test).** `sendTest()` (`OnboardingViewModel.kt:128-141`) launches a fresh 20-second job on every
  call and never cancels the previous one, and the send button stays visible and enabled during the
  wait (`OnboardingScreen.kt:231`). Tapping it at t=15s starts a second test whose
  `testSentAtEpochMs` resets `capturedMessages` to 0; the first job then fires at t=20s and sets
  `testTimedOut = true` five seconds into the new wait. It self-corrects if the copies arrive
  (`testFailed` requires `!testSucceeded`), so the harm is a flash of "No copy arrived", but it is a
  real defect. The fix is one field: keep the `Job` and `cancel()` it at the top of `sendTest`.
- **The other suspicion about the retry does not hold.** A second run is not swallowed as a repost:
  `SyntheticNotifications.postConversation` stamps each message with a fresh `now`
  (`SyntheticNotifications.kt:33,49`), and `Fingerprint.of` includes the source timestamp when the
  quality is `SOURCE_MESSAGE` (`core/reconcile/.../Fingerprint.kt:14,18`), so the second run's three
  messages are new rows and the count can reach 3 of 3.
- **`SKIPPED_PREVIEW_RESTRICTED_SUSPECTED` loses its cause in the label (D8 / H9 residue).**
  `Labels.kt:99` maps every `SKIPPED_*` code to one sentence, `diag_skipped` "Nothing usable in the
  notification, so nothing was stored" (`strings.xml:224`). That is right for most of them, but the
  preview-restricted one is exactly the diagnostic that should point at the preview advice, and it
  now reads like any other empty parse. The raw code is still shown underneath
  (`HealthScreen.kt:304`). Same shape of residue as H9's "not triggered when frequent".
- **D4's residue is the counter, not the record.** Events dropped for a disabled or paused source
  still increment `droppedAfterRevoke` (`CaptureCoordinator.kt:947,954`), shown as "dropped after
  revoke" (`strings.xml:184`) — still one bucket for four causes. The distinction the item asked for
  now lives in the gap interval instead, which names the source and is what the page renders
  (`HealthScreen.kt:270-283`). Splitting the counter is cosmetic follow-up, small.
- **A known open defect sits on D4's write path and is already recorded.** `docs/SCOPE.md:80` item
  (c): a settlement failure rolls the whole source-policy transaction back, but `HealthViewModel`
  swallows the result with `runCatching {}` (`HealthViewModel.kt:107-108`), so "stop capturing this
  app" can silently do nothing. Not part of #23, but it is the same code the D4 fix landed in.
- **Cosmetic side effect of the H4 fix.** The hero body for `PAUSED`, `RECONNECTING` and
  `GRANTED_DISCONNECTED` is now the empty string (`HealthScreen.kt:376`) because those arms used to
  carry the timestamp that moved out. `StatusHero` draws an empty `Text`
  (`core/designsystem/.../States.kt:111`). No information is lost — the timestamp is right below —
